DGX Spark 集群部署 DeepSeek-V4-Flash：2 台与 4 台的经验与可行性分析报告


数据来源：NVIDIA 开发者论坛多个实测帖（2026-05 ~ 2026-08），核心为

[GUIDE] DeepSeek-V4-Flash on 2× DGX Spark (GB10)（topic 374742），

并交叉验证 4 台专题帖（topic 373808、378878）、2 台大帖（topic 370309、368916、374846）等。

所有数字均为社区实测，硬件/版本依赖性强，请视为方向性参考而非保证值。

1. 摘要（TL;DR）


维度2 台 DGX Spark（TP=2）4 台 DGX Spark（TP=4）
---------
总统一内存256 GiB512 GiB
官方 FP8 权重 ~149 GB放得下，KV 池紧张放得下，KV 池充裕
单流 decode21–44 tok/s（FP8 基线）；DSpark 投机解码后代码类 60–67 tok/s49–54 tok/s（FP8+MTP）；配合 DSpark/NVFP4 KV 可到 90+ tok/s
聚合吞吐100–182 tok/s（1M ctx 低并发）；200K/16seqs 静态可达 ~315 tok/s150–218 tok/s @150K 缓存命中 C8–C12；decode 主导型 C16 可达 ~360 tok/s
冷启动 prefill32K≈53s、100K≈511s（弱项）50K≈20s、150K≈64s；多路冷 prefill 反而会超时失败
最大上下文1M 已验证（KV 池 1.4M–6.7M tokens 视量化路线）1M 已验证，单会话可用池 ~7.8M tokens，可支撑 ~7 路 1M 会话
成本~$8K~$20.5K–21.1K
结论**性价比与聚合吞吐之选**，双副本扩展性最好**单会话超长上下文与大 KV 池之选**，decode 提速但 prefill 无优势

**核心结论**：

1. 2 台和 4 台部署均已被社区反复验证可行，官方 FP8 权重（~149GB）是当前最稳的权重路线。

2. decode 是**内存带宽受限**——节点越多、每节点读的权重越少，单流越快；prefill 是**计算受限**——4 台对冷 prefill 几乎无帮助。

3. TP=4 不是全面优于"两台双副本"：突发多路新文档 prefill 场景下，两个独立副本反而更强。选型取决于流量形状（详见 §5.3）。

4. 稳定性三大坑（两台四台都适用）：**NCCL 必须升到 2.30.4**、**UCX 内存泄漏会拖死 UMA 主机**、**CUDA graph capture size 必须 ≥ max_num_seqs×(1+k)**。

2. 硬件与软件基线


  • **DGX Spark（GB10 / sm_121a）**：每台 128 GiB 统一 LPDDR5x（UMA，可用约 121 GiB），GPU 与主机共享同一内存池；ConnectX-7 RoCE 网卡。
  • **互联方案（论坛实测过的）**：

    • - 双机直连 QSFP56 200G DAC（link-local 地址）——2 台标准做法

    - MikroTik CRS520 200 GbE 交换机（Verel-lab 4 台）

    - MikroTik CRS504-4XQ-IN 100G 交换机 + 机间 200G 直连（voktolom 4 台）

    - QRS812 交换机 + QSFP56 400G breakout DAC（jeffery2011 4 台）

  • **模型**：`deepseek-ai/DeepSeek-V4-Flash` 官方 FP8（E4M3，约 149 GB / 46 分片）；衍生变体 W4A16-FP8（~143 GiB）、DSpark（DeepSeek 官方投机解码版）、0731 更新版。
  • **推理栈**：vLLM + SM12x 使能补丁（jasl/vllm fork，PR #40991/#41276/#41834 一脉）；NCCL 2.30.4；投机解码 MTP k=2 或 DSpark k=3。

    3.3 关键经验


    **配置要点**

  • `--kv-cache-dtype fp8 --block-size 256 --enable-prefix-caching` 是标配。
  • 早期版本必须 `--no-enable-flashinfer-autotune`（FlashInfer 正确性 bug）。
  • jasl 实测：**EP（专家并行）关掉反而更稳更快**——Spark 类互联通信是瓶颈，EP 只在高并发有理论优势。
  • `--gpu-memory-utilization` 在 GB10 上实践上限 **0.80–0.82**（0.85 每节点只剩 ~1 GiB 余量）；W4A16 路线有人跑 0.85 但系统内存占用 91–92% 属于走钢丝。

    • **稳定性坑（2 台实测）**

    1. **NCCL 版本是生死线**：默认 2.28.9 会 wedge；必须 overlay 到 2.30.4。注意 `torch.cuda.nccl.version()` 显示的是编译期常量，真实校验用 `/proc/self/maps` + `ncclGetVersion`。

    2. **UCX 内存泄漏 → 主机硬死机**（alex.busse 帖最重要的发现）：UCX 的 RDMA 注册缓存默认不释放（每请求泄漏 ~14 MB），在 UMA 架构上直接耗尽统一内存导致宿主静默卡死。修复：

    ```bash

    UCX_MEM_MMAP_HOOK_MODE=none

    UCX_RCACHE_MAX_UNRELEASED=1024

    # 兜底加固：让 OOM 可恢复而不是主机冻结

    sysctl -w vm.min_free_kbytes=3145728

    swapoff -a

    ```

    A/B 实测：不加变量 18 分钟内空闲 UMA 从 10GB 跌到 6GB 后 OOM；加了之后完全平稳。

    3. **长上下文冷 prefill 是最大体验短板**：32K≈53s、64K≈156s、100K≈511s TTFT；首次之后 prefix cache 让后续轮次亚秒级。

    4. **并发公平性**：agent 场景下一个请求的长 prefill 会饿死其他流——`--max-num-batched-tokens` 从 8192 降到 2048 可让并行流的 decode 份额提高 **2.9 倍**（1.7%→5.0%），它既是抖动杠杆也是公平性杠杆。

    5. 量化路线脆弱：W4A16-FP8 依赖精确的软件快照（vLLM commit、compressed-tensors 预发布版），换时间点的 commit 就 KeyError；**官方原生 FP8 + mp backend 是复现性最好的路线**。

    6. CX-7 链路在频繁启停后可能 wedge（mlx5 ACCESS_REG timeout），只有冷重启能恢复。

    4. 四台部署：已验证经验汇总


    三份相互独立的 4 台实测，结论部分一致、部分相反——分歧本身就是重要信息。


    4.1 Verel-lab（TP=4, jasl fork PR#41834, CRS520 200G）


  • **单流**：49.4 tok/s 标准探针，推理类峰值 54.4；工具调用仅 11.4（结构化输出吃不到投机加速）。
  • **并发**：`max-num-seqs` 从 2 调到 8 后 conc8 从 84.3 → **179.9 tok/s agg**（4 台 KV 余量大，敢于放开并发）。
  • **MTP 接受率** 0.69–0.77（略低于 2 台报告的 ~0.80）。
  • **三个坑**：

    • 1. NCCL 2.28.9 在 TP=4 下**每个长生成必 wedge**（shm_broadcast 60s 超时 → EngineDeadError → worker 变僵尸，需手工杀掉全部 4 个节点重启）；升 2.30.4 解决。

    2. jasl 镜像 ENTRYPOINT 就是 `vllm serve`，照抄 2 台脚本会命令双重叠加。

    3. triton/vllm 缓存目录必须 bind-mount，否则每次重启冷 JIT 都可能触发 wedge。

  • **decode 与上下文长度无关**（40–54 tok/s 恒定，带宽受限特征）；prefill 外推约 600–800 t/s，200K 冷 prefill 约 4–5 分钟（未实测）。

    • 4.2 jeffery2011（TP=4, QRS812 + 400G DAC, V4-Flash-0731 + DSpark + NVFP4 KV, $20.5K）


    **网络矩阵（QRS812 fabric）**：RDMA write 2.93–3.49 µs / read 5.64–6.34 µs / send 2.55–3.44 µs；iperf 105 Gbit/s；ib_write_bw 107.66 Gbit/s；CRC 错误 0。→ RoCE 交换 fabric 对 Spark 集群完全够干净。


    **C=1 基准**：


    上下文模式TTFTPrefillDecode
    ---------------
    50K冷19.6s2,548 t/s93.2 tok/s
    100K冷41.5s2,409 t/s85.3 tok/s
    150K冷64.4s2,328 t/s90.2 tok/s
    150KKV 命中0.78s（有效 193,280 t/s）90.3 tok/s

    **并发表（150K 缓存命中）**：C=6 165.5 agg / C=8 154.2 agg / C=12 208.7 agg；

    **反面证据**：C=4/C=6 的**冷独立 prompt 波次直接客户端超时**（agg 仅 1.28）——4 台也不是冷长上下文并发的解药。


    **Patch 4 血泪**：漏打 `shared_experts.gate_up_proj` 映射补丁时 decode 只有 23–26 tok/s、DSpark 接受率跌到 ~25%；补上后 decode 回到 ~90、接受率 60–95%。


    4.3 voktolom（TP=4 vs 双副本 Fleet 的严格 A/B，CRS504 100G，俄语法律分析 prose 工作负载）


    这是全论坛信息量最大的一帖，回答了"4 台到底值不值"：


    **单流 —— TP=4 明显赢**：


    指标Fleet(2×TP=2)TP=4提升
    ------------
    decode（reasoning=max）44.471.2**+60%**
    prefill pp20482,0532,615+27%
    TTFT（prefix 命中）0.40s0.29s−27%
    MTP 接受率 / 每步接受数57.3% / 2.7256.7% / 2.70不变

    接受率不变而速度大涨 → **这是带宽故事不是通信延迟故事**：4 节点时每节点每步只读 1/4 权重。


    **并发 —— 取决于谁主导**：

  • decode 主导（短 prompt 长输出）：TP=4 全面赢（C16：360 vs 230）。
  • prefill 主导（2048-token 新 prompt 批量）：**Fleet 赢**（prefill 快 26–37%，TTFT 少 46%）——两个副本在物理上并行 prefill，TP=4 却要过同一个调度器。

    • **KV 池才是 4 台的真正卖点**：

  • Fleet：2.43M + 2.39M 两个独立池，单会话上限 2.4M，并发 1M 会话 ≈ 2.36 个
  • TP=4：单一 7.80M 池，单会话可用 7.8M，并发 1M 会话 ≈ **7.44 个**
  • 附带消灭了副本间 prefix 缓存命中率漂移问题（22% vs 69%）。

    • **决定性的一个参数**：`--max-cudagraph-capture-size` 从 8 提到 64，C4 吞吐 **+170%**、C8 +148%。原理：投机解码下均匀 decode batch = seqs × (1+k)，k=3、16 slots 需要 64；capture 不够就掉进 eager，损失约 2/3 decode 速度。代价：启动 8→9 分钟。


    **他们为何仍选 TP=4**：14 天遥测显示 **96.6% 的活跃时间只有 1 个并发请求**——Fleet 的第二个副本就是闲置硬件。


    **代价**：失去滚动升级（每次重启全程 ~9 分钟停机）、爆炸半径变为整集群、冷启动更长。


    **与 jovan3 结论相左的解释**：jovan3 的 4 台（NVFP4 DS-MLA KV）decode 与 2 台打平——NVFP4 KV 把每 token 字节砍半，互联成为瓶颈，TP=4 不再划算；voktolom 用 fp8 KV @1M 窗口， firmly 带宽受限，TP=4 大幅获益。**诊断方法很便宜：盯着 accepted-tokens-per-step，若它不变而 tok/s 变化，改的是步耗时 = 带宽故事。**

    5. 可行性分析


    5.1 显存账（UMA 架构特有）


    GB10 上权重、KV、CUDA graph、进程全部共享一个统一内存池，调优空间比传统独显紧张得多：


    项目2 台4 台
    ---------
    权重占用（官方 FP8）~75 GiB/节点~37 GiB/节点
    实践 util 上限0.80–0.82（激进 0.85）同样受 UMA 约束，voktolom 用 0.85 成功
    KV 池（fp8 KV）1.43M–2.87M tokens~256 GiB / 7.8M tokens
    KV 池（NVFP4/W4A16 路线）~2M–6.68M tokens—
    并发 1M 会话能力~2.4–2.7 个~7.4 个（jovan3 称可支撑 ~14 路 1M 会话@NVFP4 KV）
    UMA 特有风险UCX 泄漏耗尽内存 → **主机冻结**（不只是进程 OOM）同样存在，节点更多暴露面更大

    5.2 性能模型


  • **Decode = 内存带宽受限**：每步每节点要把自己那份权重从 LPDDR5x 读一遍。分母越大（节点越多）每节点读得越少 → 单流提速：2台 21–44 → 4台 49–54（FP8）/ 71（prose+max reasoning）/ 90+（DSpark+NVFP4）。前提是互联足够快（RoCE 写延迟 ~3µs 完全够）；一旦 KV 量化把带宽压力减半，互联反成瓶颈，加节点收益归零（jovan3 案例）。
  • **Prefill = 计算受限**：2 台 1900–2644 t/s vs 4 台 2328–2615 t/s，几乎无差。想要 prefill 吞吐，正确答案是**多副本横向铺**而不是加大 TP。
  • **投机解码是最大的免费午餐**：MTP/DSpark 在高接受率内容（代码、格式化文本）上带来 1.5–3× 提速；但接受率依赖 batch chunk 充足（每 1 个 MTP token 至少 ~6–8K batched tokens），且低接受率还会伤质量。

    • 5.3 选型决策树


    ```

    你的流量是什么形状？

    ├─ 多用户/多 agent，短-中上下文，追求总吞吐

    │ → 2 台 × N 副本（nginx 一致性哈希），扩容线性、可滚动升级 【$8K/份】

    ├─ 单用户 agent / 长文档分析，需要 ≥500K 上下文常驻

    │ → 4 台 TP=4（7.8M token 单池 + 单流 +60%） 【~$21K】

    ├─ 突发批量新文档 prefill（如批量入库/RAG 建库）

    │ → 任意规模都建议多副本而不是大 TP；冷 prefill 并发永远别超 2–3 路

    └─ 要跑 DeepSeek-V4-Pro / Kimi / GLM-5.2 级模型

    → 8 台起（V4-Pro NVFP4 ~850GiB，8 台共 ~976GiB 可用）

    ```


    5.4 成本效益


  • jeffery2011 的 4 台整机 ~$20.5K–21.1K；jovan3 的 2 台 ~$8K。
  • 论坛共识：**如果请求可拆分，2×2 台副本的原始聚合 decode 吞吐仍然赢**（~230×2=460 vs 209，注意工作负载差异需修正）；4 台买的是"单个会话能有多大、多快"，不是总吞吐。
  • 功耗参考：4 台满载加速器合计 ~136–170W + 交换机 ~34W，非常省电。

    症状根因处置
    ---------
    长生成 ~30s 后吞吐衰减到 0，日志 `shm_broadcast: No available shared memory broadcast block` → EngineDeadErrorNCCL 2.28.9 编译期 JIT 分歧不同步升级 libnccl2=2.30.4 并 LD_PRELOAD；用 `/proc/self/maps` 验证真实加载版本

    多用户时只有一个请求在跑调度公平性问题降 `--max-num-batched-tokens` 到 2048；等上游修复
    启动报 `unrecognized arguments: serve`镜像 ENTRYPOINT 已含 `vllm serve`去掉命令里的重复前缀
    重启后每次 boot 卡在重编译未 mount triton/vllm 缓存目录bind-mount `/root/.cache/vllm` 与 triton cache

    EP 开启后更慢更不稳Spark 互联通信瓶颈干脆不开 EP（jasl 官方建议）

    7. 专题：「本轮运行失败 Provider finish_reason: network_error」为什么频发


    这个报错**不是模型输出错误，而是客户端与推理服务之间的 HTTP/SSE 流中断或超时**，被 agent 客户端统一归因成 network_error。结合论坛证据，按出现概率排序：


    **① 冷 prefill 超过客户端超时（最常见）**

    长上下文首 token 时间极长：2 台 32K≈53s、128K≈250s、100K 可达 511s（~8.5 分钟）；4 台冷 150K 也要 ~64s。多数 OpenAI SDK / agent 工具（opencode 等）默认请求超时只有几十秒到几分钟，服务端还在 chunk prefill，客户端先掐线 → network_error。jasl 在帖子里诊断过一个一模一样的案例（opencode 固定在 ~64K 处断）。

    *处置*：客户端调大/禁用 request timeout；开 streaming；利用 prefix caching 让同会话第二轮起亚秒返回；给 agent 加 warmup。


    **② 引擎中途死亡，流被重置**

    NCCL 2.28.9 wedge（EngineDeadError → 容器自动重启）或 UCX 泄漏导致的 UMA OOM abort，都会把正在进行的 SSE 流硬切断。特征：短请求一直正常、长请求必挂，或者随 uptime 增加越来越频繁。

    *处置*：按 §6 前两行修；配 systemd/watchdog 自动拉起，把崩溃变成 10 秒中断而不是永久失联。


    **③ 代理层空闲超时**

    若像 voktolom 那样前面挂 nginx：`proxy_read_timeout` 默认 60s，长 prefill/长思考期间没有字节流出就会被代理掐断。

    *处置*：代理对该路由 read timeout ≥600s，关闭缓冲。


    **④ 并发饥饿导致的流内长停顿**

    别的会话在做长 prefill 时，你的流可能每秒只能挤到 0.6–1.9 token，中间 gap 数十秒，触发客户端 idle timeout。

    *处置*：`--max-num-batched-tokens 2048`；错峰提交大上下文请求。


    **⑤ 多节点基础设施抖动**

    CX-7 链路 wedge（需冷重启）、GID index 因 IP 重排失效、worker 僵尸化 broken-pipe 循环、SSH 层层引号弄坏 JSON 参数导致节点没真正加入——任何一种都会让请求挂在半路。

    *处置*：报错时间点对照 4 个节点的引擎日志与 `dmesg`（看 oom-killer/hung task）；监控各节点 free UMA 趋势曲线判断是否泄漏复发。


    **排查顺序建议**：先用 curl 直连推理端口、超时设 900s 复测同一 prompt——直连成功即客户端/代理问题；直连也断则查服务端日志（EngineDeadError / shm_broadcast / OOM / UCX），基本都能对号入座 §6 速查表。
